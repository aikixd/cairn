# Cairn Workflow & Instructions

**Context**: This workspace uses the `cairn` tool to maintain a persistent code map.
**Mandate**: All code changes must adhere to the tagging rules defined below to ensure the map remains accurate.

## 1. Activation
**Status: ALWAYS ACTIVE**
You are required to use the Cairn tagging workflow for all code modifications in this session.
*   **Assumption**: The user intends to use Cairn. Do not infer "Inactive" status from empty directories or missing files.
*   **Missing Tool**: If `cairn` is not installed, **apply tags anyway**, then notify the user that map generation skipped.

## 2. Core Philosophy: High Signal, Low Noise
The goal of Cairn is to create a **human and LLM navigable map**, not a complete symbol table.
*   **Curated**: Only tag items that are structurally significant.
*   **Concise**: Explain *why* an item exists, not just *what* it does.
*   **Exclusive**: If in doubt, **DO NOT TAG**. A cluttered map is worse than an empty one.
*   **Discoverability**: Do not tag things that are immediately discoverable from other tagged items. If a reader would naturally encounter it by reading a tagged type or entering a tagged function, skip it.

## 3. The Protocol

### Phase A: Discovery (Read-First)
Before writing code or answering complex questions, you MUST:
1. Check for `docs/map.generated.md`.
2. If it exists, READ IT.
3. Use the map to locate `entry` points, `core` types, and `invariant` rules.

### Phase B: Planning (Task integration)
When creating your implementation plan, you MUST explicitly include tagging steps.
1. Identify which new/modified components will require tags (`core` structs, `entry` points).
2. Add a specific checklist item for tagging: `- [ ] Add/Update Cairn tags for [Component]`

### Phase C: Implementation (Tag-When-Appropriate)
Every time you scaffold, write or modify significant code (Structs, Enums, Public Functions, Modules), evaluate whether it meets the criteria below. Apply tags only when it does.

**Syntax Rules:**

1.  **Format**:
    ```rust
    /// [nb:<TYPE>] <Optional Key=Value> <Summary Line>
    /// <Description Body>
    ```
    *   `TYPE`: Must be one of `entry`, `core`, `invariant`, `recipe`.
    *   `Key=Value` (Optional): Metadata like `rfc=001` or `complexity=high`.
    *   `Summary`: Can start on the same line OR the next line.
    *   `Termination`: The description ends at the first **blank doc-comment line** or **non-doc line**.

**Forbidden / Incorrect Patterns (DO NOT USE):**
*   ❌ `// [nb:core]` (Double slash is ignored. Use `///`)
*   ❌ `[nb:core]` (Missing comment syntax)
*   ❌ `/// [nb:unknown]` (Invalid type)

**Rendering Logic (How it appears in the map):**

*Input Code:*
```rust
/// [nb:core] complexity=high
/// Central state machine for the consensus engine.
/// Handles leader election and log replication.
///
/// This part is NOT included in the map summary (after blank line).
pub struct Consensus { ... }
```

*Output Map Entry:*
> **Consensus** (core)
> Central state machine for the consensus engine. Handles leader election and log replication.
> *Metadata*: complexity=high

**Tag Types:**
*   **`core`**: Domain concepts and architectural hubs — the terms you use when *narrating how the system works*, not how it is implemented.
    *   Applies to: structs, enums, traits, **and modules**. A module that consolidates all tasks, handlers, or operations for a subsystem is `core` even if individual items in it are not.
    *   *Heuristic*: Would you use this term when explaining the system to a new developer? Tag the story-level concepts (`ControlFlowGraph`, `BasicBlock`), not the implementation details that fall out of them (`Edge` is implied by any graph — skip it).
    *   *Discoverability test*: If a reader would encounter it naturally by reading another tagged item, do not tag it.
    *   *Avoid*: Implementation details, data bags, companion enums that merely enumerate options for a tagged type, display/formatting code.

*   **`invariant`**: Critical constraints — "Never do X", "Always do Y", security boundaries.
    *   Tag the *defining* type or location that establishes the constraint, not every site that enforces it.
    *   MUST explain the consequence of violation in the description.

*   **`entry`**: Execution roots with a **temporal basis** — a function, method, or invocation point that triggers a process.
    *   A type or module is **never** `entry`, even if important. Important types are `core`.
    *   *Library code*: the boundary function a caller invokes to use a subsystem (e.g. `translate_to_vir()`, `Vehicle::load()`).
    *   *Application code*: CLI commands, event handlers, main threads.
    *   *Counter-example*: `VirValidator` is `core`. The function that calls `validate()` is `entry`.

*   **`recipe`**: Idiomatic patterns, organizational helpers, and structural code that shapes how the codebase is understood.
    *   *Usage*: Types, macros, or functions that answer "How do I do X in this codebase?" They exist for organization and discoverability reasons, not necessarily because they carry critical logic.
    *   *Examples*: Test builders, type-safe ID wrappers, builder patterns with non-obvious ordering constraints, arena allocation helpers.
    *   Tag test support code when it is a pattern others should reuse.

### Phase D: Synchronization
After modifying code:
1. Run `cairn gen` to update the map.
2. Check the command output.
    *   *If errors reported*: Fix syntax/location and retry.
    *   *If success*: Proceed.

## 4. Project-Specific Addendums
- **RFC metadata**: Omit `rfc=` metadata from tags until ADR→RFC migration is complete (RFC-0001, RFC-0002 pending). Descriptions should be self-documenting in the meantime.
