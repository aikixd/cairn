## Tool Discovery & Initial Learning

### How you probably got here

1. User said something like: "learn to use `cairn`" or "use the cairn tool"
2. You ran `cairn --help` and saw `llm-desc` and `llm-skill` commands
3. You ran `cairn llm-desc` to understand what it does
4. Now you're reading this for the complete workflow

### What this tool does

`cairn` generates curated code maps from developer-tagged landmarks in Rust codebases. Think of it as a human-maintained "table of contents" for code, showing:
- **Entry points** (where execution starts)
- **Core concepts** (domain model and architecture)
- **Invariants** (rules that must not be violated)
- **Recipes** (reusable utilities and patterns)

Output: `docs/map.generated.md` - a browsable, grouped map of tagged items.

## Reading Existing Code Maps

### Step 1: Check for the map

Always look for `docs/map.generated.md` first when exploring a codebase:

```bash
ls docs/map.generated.md
# If exists: read it first before diving into code
```

### Step 2: Interpret the structure

The map is organized by tag type:

- **`entry`**: Start here to trace execution flow
  - Main functions, CLI handlers, API boundaries
  - Subsystem entry points
  
- **`core`**: Understand the domain model
  - Key data structures and types
  - Architectural components
  - Business logic abstractions

- **`invariant`**: Critical constraints - READ BEFORE MAKING CHANGES
  - Rules that must not be violated
  - Architectural decisions from RFCs
  - "Never do X, always do Y" patterns
  
- **`recipe`**: Reusable solutions
  - Helper functions for common tasks
  - Macros that reduce boilerplate
  - Standard initialization patterns

### Step 3: Navigate efficiently

1. Find relevant `entry` points for your task
2. Check related `core` types to understand data flow
3. **Review `invariant` tags** to avoid violating constraints
4. Check `recipe` tags before implementing utilities (avoid reinventing)

### Step 4: Generate if missing/stale

If the map doesn't exist or seems outdated:

```bash
cairn gen
# Default: scans codebase, outputs to docs/map.generated.md
# Tag prefix: 'nb' (configurable via --prefix)
```

## CRITICAL: Writing Code with Tags

### ⚠️ THE CARDINAL RULE ⚠️

**When you write new code, you MUST add appropriate tags. Without tags, the map becomes stale and useless.**

This is not a "nice to have" - it's a core workflow requirement. If you forget to tag, you're breaking the tool.

### How to remember (your responsibility)

Add this to your task.md workflow when working on codebases that use this tool:

```markdown
## Implementation
- [ ] Write code
- [ ] Add appropriate tags (entry/core/invariant/recipe)
- [ ] Verify tags are well-formatted and descriptive
- [ ] Regenerate map: `cairn gen`
```

### Tag selection criteria

#### Use `entry` when:
- Creating a main function or CLI command handler
- Adding a public API function that's a natural starting point
- Implementing a subsystem entry point (e.g., `Scanner::scan`, `Parser::parse`)

```rust
/// [nb:entry]
/// CLI entry point. Orchestrates command parsing and dispatch.
fn main() -> Result<()> { ... }
```

#### Use `core` when:
- Defining a type that represents a core domain concept
- Creating a struct/enum central to the architecture
- **Don't use** for helpers, builders, or trivial types

```rust
/// [nb:core]
/// Represents a tagged code item with location, summary, and metadata.
/// Used to build the generated code map.
pub struct MapEntry {
    pub tag: String,
    pub anchor: String,
    pub file: PathBuf,
    // ...
}
```

#### Use `invariant` when:
- Documenting a constraint that MUST NOT be violated
- Near code that enforces a critical rule (macros, validators)
- Capturing RFC decisions that should never be undone
- Warning about anti-patterns

```rust
/// [nb:invariant] rfc=RFC-0007
/// Never hand-roll integer wrappers; always use `define_named!` macro.
pub macro define_named { ... }
```

#### Use `recipe` when:
- Creating a utility that solves a tricky problem
- Building a macro that reduces boilerplate
- Implementing a standard pattern others should reuse

```rust
/// [nb:recipe] tags=workspace
/// Recursively discovers all Cargo.toml files and resolves crate names.
/// Handles workspaces, excluded members, and nested repositories.
fn resolve_crate_map(root: &PathBuf) -> Result<HashMap<PathBuf, String>> { ... }
```

### Tag format

```rust
/// [nb:tag_name] optional_key=value key2=value2
/// Description goes here. Be concise but clear.
/// Multiple lines are OK. Stop at first blank /// or non-doc line.
pub fn my_function() { ... }
```

**Metadata keys** (all optional):
- `tags=foo,bar,baz` - Additional categorization
- `rfc=RFC-0007` or `rfc=docs/rfcs/RFC-0007-foo.md` - Link to RFC
- `recipe=docs/recipes/foo.md` - Link to recipe document
- `owner=teamname` - Ownership attribution
- Custom keys as needed for your workflow

## Integrating with Existing Workflows

### RFC-driven development

If you create/modify code based on an RFC, reference it:

```rust
/// [nb:invariant] rfc=RFC-0023
/// All database queries must use prepared statements.
```

This creates traceability: future agents can trace the decision back to the RFC.

### Recipe/documentation links

If you write a utility that implements a documented pattern:

```rust
/// [nb:recipe] recipe=docs/recipes/error-handling.md
/// Creates a standardized error context with file/line info.
```

### Task tracking integration

When working through a task.md, add a tagging checkpoint:

```markdown
## Phase 2: Implementation
- [ ] Implement UserService
- [ ] Add [nb:core] tag to UserService
- [ ] Implement authentication flow
- [ ] Add [nb:entry] tag to authenticate() handler
- [ ] Add invariant tag for "never store plaintext passwords"
```

### Custom metadata

Use custom keys to track whatever matters for your project:

```rust
/// [nb:core] epic=auth-v2 pr=1234
/// OAuth2 token manager with refresh capability
```

## Examples

### Example 1: Adding a new CLI command

```rust
/// [nb:entry]
/// Validates that generated map matches checked-in version.
/// Used in CI to detect stale maps. Exit 0 if match, 1 if diff.
fn check_command(root: &Path) -> Result<()> {
    // implementation
}
```

**Why this tag?**
- It's an entry point (CLI command handler)
- Description explains what it does and when it's used
- Concise and actionable

### Example 2: Core domain type

```rust
/// [nb:core]
/// File scanner that discovers Rust source files in a workspace.
/// Respects .gitignore and excludes target/, .git/, etc.
pub struct Scanner {
    root: PathBuf,
    excludes: Vec<Pattern>,
}
```

**Why this tag?**
- Central to the architecture (file discovery is a core concept)
- Not a helper - it's a significant abstraction
- Description captures its role and behavior

### Example 3: Invariant

```rust
/// [nb:invariant] rfc=docs/rfcs/workspace-resolution.md
/// ALL crate resolution MUST use recursive metadata discovery.
/// Never rely solely on workspace.members - it misses excluded/nested crates.
/// See RFC for edge cases (nested workspaces, excluded members).
fn resolve_crate_map(root: &PathBuf) -> Result<HashMap<PathBuf, String>> {
    // implementation that correctly handles edge cases
}
```

**Why this tag?**
- Documents a critical constraint from architectural decision
- References the RFC for full context
- Prevents future refactoring that breaks edge case handling
- "Never do X" language is clear

### Example 4: Recipe

```rust
/// [nb:recipe] tags=testing
/// Creates a temporary test workspace with specified crate structure.
/// Use in tests to avoid coupling to fixture directory layout.
fn create_test_workspace(crates: &[(&str, &str)]) -> TempDir {
    // implementation
}
```

**Why this tag?**
- Reusable utility pattern for tests
- Other tests should use this instead of reinventing
- Tagged so future agents find it when writing tests

### Example 5: Integrating with RFC workflow

```rust
/// [nb:invariant] rfc=RFC-0042
/// Map generation MUST be deterministic (stable ordering, normalized whitespace).
/// Enables git-diffable output and CI validation.
/// See RFC-0042 section 3 for determinism requirements.
```

**Before writing this code**, the agent:
1. Read the RFC
2. Understood the determinism requirement
3. Implemented the feature
4. Added the invariant tag to document the constraint
5. Referenced the RFC so future changes can trace back to the decision

This creates a feedback loop: RFCs inform code, tags reference RFCs, agents read tags, agents consult RFCs.

## Advanced: Installation & Setup

### Installing the tool

```bash
# From crates.io (when published)
cargo install cairn

# From source
git clone <repo>
cd cairn
cargo install --path .
```

### Setting up a new project

```bash
cd your-project
cairn gen  # Creates docs/map.generated.md
git add docs/map.generated.md
git commit -m "Add initial code map"
```

### CI Integration

Add a CI check to ensure the map stays current:

```yaml
# .github/workflows/ci.yml
- name: Verify code map is current
  run: |
    cairn gen
    git diff --exit-code docs/map.generated.md
```

(Note: `cairn check` command for this is planned but not yet implemented)

## FAQ

**Q: What if I'm not sure whether to tag something?**
A: Err on the side of not tagging. Only tag things that are genuinely significant landmarks. Over-tagging defeats the purpose.

**Q: Can I use custom tag names?**
A: No - stick to entry/core/invariant/recipe. Custom tags won't be recognized.

**Q: What if the codebase doesn't have a map yet?**
A: Run `cairn gen` to create one. If nothing appears, the codebase hasn't been tagged yet - you'd be the first to add tags.

**Q: How do I handle multi-crate workspaces?**
A: The tool automatically discovers all crates (workspace members, excluded crates, nested workspaces). Tags from all crates go into one unified map with crate names as prefixes.

**Q: Can I change the tag prefix from 'nb'?**
A: Yes, use `--prefix custom` when generating. But you should use whatever prefix the project already uses.
